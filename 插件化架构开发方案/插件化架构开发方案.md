Android Agent 全量插件化架构方案

一、项目目标

目标不是简单给 Android Agent 增加几个插件。

而是建立一个类似 DeepSeek Harness / Cordis 的：

Everything is a Plugin Agent Runtime

即：

Android Host │ └── Plugin Runtime │ ├── Agent ├── Agent Loop ├── Model ├── Tool ├── Skill ├── Memory ├── Session ├── Workflow ├── MCP ├── Sandbox ├── UI ├── Command ├── Service ├── Event └── Storage 

Host 的职责不是实现这些业务能力，而是：

加载 管理 组合 隔离 授权 卸载 更新 恢复 

二、最重要的架构原则

整个系统分为两个世界：

┌────────────────────────────────────┐ │ Android OS Layer │ │ │ │ Package / Manifest / Permission │ │ Activity / Service / Process │ │ App Sandbox / System API │ └──────────────────┬─────────────────┘ │ │ Android 提供的边界 ↓ ┌────────────────────────────────────┐ │ Agent Runtime Layer │ │ │ │ Everything is Plugin │ │ │ │ Agent / Model / Tool / Memory ... │ └────────────────────────────────────┘ 

真正能够做到“Everything is Plugin”的范围，是第二层。

第一层仍然受到 Android OS 的约束。

三、哪些东西可以完整插件化

这些原则上都可以由 Plugin 实现。

1. Agent

Agent Agent Loop Planner Reasoner Subagent Orchestrator 

例如：

Default Agent Codex Agent DeepSeek Agent Custom Agent 

都可以互相替换。

2. Model

可以插件化：

DeepSeek Qwen Kimi GLM OpenAI Anthropic 本地模型 自定义 API 

包括：

Model Provider Authentication Streaming Tool Calling Model Capability Context Management 

3. Tool

例如：

Git GitHub Browser Terminal Filesystem HTTP Database MCP 

都可以作为 Plugin。

4. Memory

Conversation Memory Vector Memory SQLite Memory File Memory Remote Memory 

可以互相替换。

5. Session

Session Manager Conversation Manager History Persistence Checkpoint 

都可以插件化。

6. Skill

Coding Skill Android Skill Git Skill Research Skill Writing Skill 

可以动态安装和卸载。

7. Workflow

例如：

Coding Workflow Research Workflow Debug Workflow Review Workflow 

可以成为 Plugin。

8. MCP

MCP Client、Server Adapter、Tool Provider 都可以插件化。

9. UI

业务 UI 可以插件化：

Chat UI Tool UI Git UI Terminal UI Browser UI Settings UI Plugin UI 

Host 提供 UI Shell，Plugin 提供业务界面。

10. Event / Hook

AgentStarted ModelCalled ToolCalled ToolFinished SessionCreated SessionClosed 

都可以由 Plugin 注册。

四、哪些东西不能直接插件化

这里是整个方案最重要的部分。

1. Android Manifest 不能动态插件化

这是一个明确的边界。

例如 Plugin 想声明：

<uses-permission android:name="android.permission.CAMERA"/> 

不能因为用户安装了 Plugin，就让 Android 动态修改 Host 的 Manifest。

因为 Manifest 属于：

Android Package 层

而不是你的 Plugin Runtime。

所以：

Plugin ↓ 请求 CAMERA ↓ Android Manifest 

不能动态增加。

五、Android 权限不能由普通 Plugin 自己获得

这是你刚才特别指出的问题。

例如：

Camera Plugin 

想获得：

android.permission.CAMERA 

不能简单：

安装 Plugin ↓ Plugin 自动获得 CAMERA 

不成立。

真正的结构应该是：

Plugin ↓ Permission Request ↓ Host Permission Manager ↓ Host 是否拥有 CAMERA？ 

如果 Host 已经拥有：

CAMERA 

那么：

Host ↓ 授权 Plugin 使用 Camera Service 

如果 Host 根本没有：

CAMERA 

那么 Plugin 不能凭空获得。

六、所以权限应该分成两层

Android 权限

例如：

CAMERA RECORD_AUDIO ACCESS_FINE_LOCATION BLUETOOTH POST_NOTIFICATIONS 

这些属于：

Android OS 

必须由 Host APK 声明并经过 Android 权限机制授权。

Plugin 权限

这是我们自己定义的：

filesystem.read filesystem.write network shell credential database camera microphone 

例如：

GitHub Plugin 

请求：

network credential.github 

Host 决定是否允许。

七、正确的权限结构

应该是：

Plugin │ ↓ Plugin Permission │ ↓ Permission Manager │ ┌───────┴────────┐ ↓ ↓ Android Permission Runtime Permission │ │ CAMERA filesystem LOCATION network AUDIO credential │ │ └───────┬────────┘ ↓ Plugin Service 

这样 Plugin 永远不直接控制 Android 权限。

八、哪些 Android 系统组件不能真正插件化

下面这些不能按照普通业务 Plugin 的方式无限动态增加：

Activity

不能：

安装 Plugin ↓ Android 自动多一个 Activity 

但可以：

Host Activity ↓ Plugin UI 

Service

不能把 Plugin Service 当成：

Android Manifest 中新的 Service 

动态注册。

但是可以：

Host Service ↓ Plugin Service Interface 

由 Host Service 代理。

BroadcastReceiver

同理。

Plugin 可以：

EventBus 

而不是依赖 Android Manifest 动态增加 Receiver。

ContentProvider

也不能随意动态增加。

应该通过：

Host Provider ↓ Plugin Storage Service 

实现。

九、Notification

Notification 本身可以插件化。

例如：

Plugin ↓ NotificationService ↓ Host ↓ Android Notification 

但真正的 Android Notification 权限：

POST_NOTIFICATIONS 

仍然属于 Host。

十、后台运行

这是 Android 特别大的限制。

不能认为：

Plugin ↓ 无限后台运行 

Android 会对后台进程、后台服务、电量等进行限制。

因此应该：

Plugin ↓ Scheduler ↓ Host ↓ Android JobScheduler / WorkManager / Foreground Service 

也就是说：

后台执行机制必须由 Host 统一管理。

十一、文件系统不能完全插件化

Plugin 可以拥有自己的：

Plugin Storage 

但是不能默认：

访问整个 Android 文件系统 

应该：

Plugin ↓ FileSystem Service ↓ Permission Manager ↓ 允许的目录 

例如：

Plugin A ↓ /plugins/A/data 

默认不能访问：

/plugins/B 

十二、Shell / Terminal

这个可以做成 Plugin：

Terminal Plugin 

但是：

Android 上不存在一个默认等同于桌面 Linux 的无限制系统 Shell。

因此：

Terminal Plugin 

实际能力取决于：

Android Termux Root Container Sandbox 

等环境。

所以 Terminal 可以插件化，但底层系统能力不是 Plugin 自己创造出来的。

十三、Root 权限

Root 不是 Plugin 权限。

如果设备有 Root：

Host ↓ Root Service ↓ Plugin 

可以调用。

如果没有 Root：

Plugin 

不能通过插件系统凭空获得 Root。

十四、Native / Rust

Native 能力可以插件化。

例如：

Plugin ↓ Rust ↓ .so 

但它仍然运行在：

Host Process 

时，安全级别和 Host 非常接近。

所以：

Native Plugin 不是安全沙箱。

十五、真正不可信的 Plugin 怎么办？

这是整个系统必须解决的问题。

如果：

GitHub ↓ 第三方 Plugin ↓ DexClassLoader 

它和 Host 在同一进程运行，那么恶意代码理论上可能：

读取 Host 内存 访问 Host 对象 调用 Host 权限 读取敏感数据 

所以：

Trusted Plugin

可以：

Host Process 

运行。

Untrusted Plugin

应该：

Host Process │ │ IPC ↓ Plugin Process 

进一步：

Plugin Process ↓ Restricted Service ↓ 限制文件 限制网络 限制 Token 限制系统调用 

十六、所以 Plugin 实际上应该有安全等级

Level 0 纯配置 / Skill / Prompt 

最安全。

Level 1 普通 Kotlin Plugin 

Host Runtime。

Level 2 Native Plugin 

Kotlin + Rust。

Level 3 Privileged Plugin 

Shell / Root / 系统能力。

Level 4 Untrusted Plugin 

独立进程 / 强隔离。

十七、签名不是 Android APK 签名

这里也需要明确。

因为 Plugin 不是普通 Android APK。

我们可以建立自己的：

Plugin Signature 

例如：

Developer ↓ Private Key ↓ Plugin ↓ Signature 

Host：

Plugin ↓ Public Key ↓ Verify 

这样可以区分：

官方插件 可信开发者 未知插件 

十八、插件更新也不能破坏 Host

插件升级：

A v1 ↓ A v2 

必须：

下载 ↓ 验证 ↓ 加载到新 ClassLoader ↓ 初始化 ↓ 健康检查 ↓ 切换 ↓ 卸载旧版本 

而不是：

删除旧插件 ↓ 加载新插件 

否则新插件启动失败，整个 Agent 可能瘫痪。

十九、核心 Agent 是否能完全插件化？

可以。

这是整个方案与传统 Android 插件系统最大的区别。

可以：

Host ↓ Plugin Runtime ↓ Agent Plugin ↓ Agent Loop 

而不是：

Host ↓ Agent Core ↓ Plugin 

因此：

Agent Model Tool Memory Session Workflow 

全部可以是 Plugin。

二十、但 Plugin Runtime 本身不能全部插件化

这里还有一个非常关键的底线。

必须存在一个最小 Kernel：

Plugin Kernel 

它负责：

Plugin Loading Lifecycle Registry Event Dependency Permission Storage Isolation 

否则：

Plugin ↓ 加载 Plugin ↓ 谁负责加载？ 

会产生无限递归。

所以：

Agent Core 可以插件化，但 Plugin Runtime / Kernel 必须保留在 Host。

这就是 Android 版“Everything is a Plugin”的真正底层边界。

二十一、最终应该形成三个层次

┌───────────────────────────────┐ │ Android OS │ │ │ │ Manifest / Permission / IPC │ │ Process / Storage / System │ └───────────────┬───────────────┘ │ ┌───────────────▼───────────────┐ │ Plugin Kernel │ │ │ │ Loader │ │ Registry │ │ Lifecycle │ │ Event │ │ Dependency │ │ Permission │ │ Isolation │ └───────────────┬───────────────┘ │ ┌───────────────▼───────────────┐ │ Agent Plugins │ │ │ │ Agent │ │ Model │ │ Tool │ │ Memory │ │ Session │ │ MCP │ │ Skill │ │ Workflow │ │ UI │ │ Sandbox │ └───────────────────────────────┘

二十三、最终结论

所以这个项目不是“把 Android App 做成插件 APK”。

真正应该定义成：

Android Host + Plugin Kernel + Everything-is-a-Plugin Agent Runtime。

其中：

Android OS ↓ Host APK ↓ Plugin Kernel ↓ Everything is Plugin 

Host 是 Android 的边界。

Plugin Kernel 是系统的最小不可插件化核心。

Agent Application Layer 基本全部插件化。

而 Android 的：

Manifest

Package

系统权限

Process

Activity

Service

Provider

OS API

仍然属于 Host / Android OS 层。

特别是权限：Plugin 不能自己获取 Android 权限，而是必须通过 Host 的 Permission Manager；Host 没有声明或没有获得的 Android 权限，Plugin 不能凭插件本身突破。

这才是比较严谨的 “DeepSeek Harness/Cordis 思想在 Android 上的可落地版本”，而不是简单地把电脑端插件机制照搬到 Android。
